# Bridge Plan: From Primitive Workbench To Dashboard Compiler

Date: 2026-09-03 (revision 4, same day; corrections from the independent review folded into the beads)
Status: plan space. Nothing in this document is implemented until a bead says so.
Supersedes the "Near-Term Backlog" ordering in `docs/roadmap.md`. Items 6
(structured diagnostic codes), 7 (filter remainder), 8 (decomposition tree),
9 (filter pane styling) and 12 (ops replay) were only absorbed by beads added
in refinement round 4 on 2026-09-03; the bead set, not this document, is the
authoritative backlog. `docs/pilot-lessons.md` remains the field-evidence source.

## Why this plan exists

The 2026-09-03 reality check found the code honest and solid on the first half
of `goal.md` (offline-safe authoring, agent contract, primitives, Microsoft
integration) and thin on the second half (a compiler that builds any dashboard
from schema/profile/intent, a visual design layer, and automated Desktop
proof). Zero open beads covered the remaining vision. This plan closes every
gap the check found, in dependency order, so that an agent can take an unknown
schema and produce a Power BI project that is correct, offline-safe, and
visually excellent on the first Desktop open.

## The one-command story this plan must make true

```bash
powerbi-cli report compose \
  --schema sales.schema.json --rows sales.sample.csv \
  --intent sales.intent.md --style corporate-neutral \
  --out-dir build/sales --json
```

returns, in one response: the inferred profile, the plan decisions with
reasons, the compiled v2 spec, the op plan that was applied, a scorecard
(strict validation, Microsoft validator when installed, lint, design lint,
handoff safety, proof level), an SVG wireframe path per page, and the exact
next commands for Desktop proof. Every intermediate artifact is written beside
the project so an agent can inspect, edit, and re-run any single stage. If any
stage needs input the agent did not give, the response is a structured
`missing_input` with the exact field, not a default.

## Product bar for "excellent and beautiful"

An agent using only this CLI must be able to produce a report that a Power BI
practitioner would accept as a finished, on-brand deliverable. Concretely, the
generated report must satisfy the design defaults in T5.0 out of the box:
8-pixel spacing scale, 12-column grid, KPI strip of equal-width cards, at most
eight visuals per page, page heading and section dividers, sentence-case
left-aligned titles, one accent color plus neutrals with semantic status
colors, subtle gridlines, axis titles only when not obvious, data labels on
bars and cards but not on dense lines, descending sort on ranking bars, number
formats and display units matched to the data, slicers in a consistent rail
that stays in sync across pages, a back button on drillthrough pages, no
clipped controls, no blank visuals after refresh, no Desktop issue banners.

## Ground rules carried forward

- Supported features emit real PBIR/TMDL; unproven ones return
  `unsupported_feature`. No guessed JSON.
- Desktop is the oracle. Proof ladder stays
  `unit-smoke < schema-golden < desktop-golden-pending <
  manual-desktop-canvas-refresh < desktop-canvas-refresh`.
- New PBIR shapes come from Desktop-authored references only. Four MIT-licensed
  `microsoft/BCApps` PBIR files (pie, donut, matrix as `pivotTable`, slicer)
  are archived under `docs/reference/desktop-authored-visuals/`; the combo
  reference there was generated by this repo and Desktop-saved. Everything
  else must be authored in Desktop first (the reference-corpus bead), then
  archived with the T9.7 harvester. Attribution is recorded per file.
- Every mutation supports `--dry-run`, `--out-dir`, or guarded `--in-place`
  and returns readback/validate/next commands.
- No monolith. Each slice lands in a focused module with tests.
- Data-domain agnostic. Archetypes, not domains, define the product.
- Docs, skill, `capabilities`, and `features list` change in the same commit
  as the behavior.
- Offline safety is never traded for beauty: images are registered resources
  with size caps and no external URLs, conditional-formatting thresholds are
  flagged like filter literals, snapshots live outside the project.

## T0. Contract repairs, harness, tooling

### T0.1 Reject unknown dashboard spec keys

Finding: `report spec validate` and `report build` accept a spec with unknown
top-level keys (for example `measures` or `filters` placed at the root instead
of under `model` or `pages[]`) and return `ok:true` with no warning. The build
silently drops them. This violates the no-silent-guessing rule and will get
worse as the spec grows.

Work:

- Add a strict spec walker (new `report_spec_schema.rs`) that knows the
  allowed key set at every level: root, `report`, `model`, `model.measures[]`,
  `pages[]`, `pages[].visuals[]`, `pages[].visuals[].bindings[]`,
  `pages[].interactions[]`, `style`, `proof`.
- Unknown key produces an error with code `spec.unknown_field`, a JSON pointer
  path, and a `didYouMean` suggestion using the existing did-you-mean helper.
- Keys that are recognized but not yet compiled (page `filters`, `style`,
  `model.relationships`) keep returning `unsupported_feature` with the exact
  next command; that path already exists and must stay until T3 lifts it.
- `report spec validate` without `--schema` (shape-only mode) must also run
  the walker.

Tests: unit test per level with a misplaced key; e2e CLI test that the
extended spec from the reality check fails with the pointer `/measures`;
conformance test that every `unsupported_feature` spec key is listed in
`report spec fields` output; property test that random key insertion at any
depth is always rejected with a pointer that resolves in the input.

## T1. Operation IR

### Why

Every mutation kernel today is `fn(args: &[String]) -> CliResult<Value>`.
The compiler cannot call them without synthesizing argv strings, which is
fragile and untestable. A typed operation layer gives one contract to four
consumers: the CLI parser, the dashboard compiler, the replay/apply surface,
and the design auto-improve loop (T5.5). It also makes the metamorphic
property testable: building from a spec that contains X must equal building
without X and then applying op X.

### Design

- New module family `ops/`: `ops::Op` enum, `ops::OpPlan`, `ops::OpOutcome`,
  `ops::ProjectContext`, `ops::Transaction`.
- Each kernel is split into `parse_args(&[String]) -> Op` and
  `apply(&Op, &mut Transaction) -> OpOutcome`. The CLI path becomes
  `parse_args` then `apply`; output JSON is unchanged (proven by goldens and
  the artifact-parity corpus).
- `Op` is `serde` round-trippable as `powerbi-cli.ops.v1` JSON with stable
  field names. Handles inside ops are the same public handles agents already
  see.
- Deterministic handle derivation: an op that creates an object declares the
  handle it will produce, derived from the spec id with the same slug rules
  scaffold already uses (`visual:<PageName>:VisualContainer<Slug>`), so later
  ops in the same plan and later agent sessions can reference it without a
  readback. Collisions are plan-validation errors.
- `OpPlan` validates handle references between ops, detects duplicates,
  orders model ops before report ops and page ops before visual ops, and
  reports the plan as a DAG with `stage` numbers.
- Transactional apply: a `Transaction` stages every file write in memory,
  runs the complete plan, runs strict validation on the staged tree, and only
  then commits atomically to the out-dir or (for `--in-place`) after writing
  a sibling snapshot. Any op failure or validation failure discards the
  transaction and returns the failing op index, its error, and the ops that
  had succeeded, so an agent can fix one op and replay. This generalizes the
  existing "restore the original TMDL on failed validation" behavior to every
  kernel.
- `OpOutcome` carries `changes[]`, readback commands, warnings, and created
  handles so the compiler can aggregate them into the build response.
- Every op is idempotent by declaration: applying the same op twice is either
  a no-op with `changed:false` or a validation error, never a duplicate.

### T1a Core (single owner, blocks everything)

IR types, plan validation, transaction, and the eight kernels the compiler
needs first: `AddMeasure`, `AddRelationship`, `AddVisual` (including
card/slicer/textbox shorthands), `AddFilter`, `SetDrillthrough`,
`SetInteraction`, `ApplyThemePreset`, `SetObject`.

### T1b Completion (parallel after T1a)

`AddCalculatedColumn`, `AddStaticTable`, `SetSortBy`, `SetBindings`,
`SetPosition`, `SetDisplayName`, `SetTopNGuard`, `ClearFilter`,
`SetDrilldownHierarchy`, `ApplyThemeBundle`, `ApplyStyleBundle`, `AddPage`,
`ClonePage`, `ReorderPages`, `SetActivePage`, `SetText`, `SetColor`,
`FormattingApply`, `SlicerClear`, `BookmarkMetadata`, `SanitizeAction`.

Tests: round-trip serde test for every variant; per-kernel equivalence test
that `parse_args` then `apply` produces byte-identical projects to the current
path (artifact-parity harness reused); plan validation negative tests for
dangling handles, duplicates, collisions, and wrong ordering; transaction
tests that a failing op in the middle of a plan leaves the out-dir absent and
the in-place project untouched; idempotency test per op.

Non-goals: no raw PBIR/TMDL patch op. Ops are typed and validated, never a
side door.

## T2. Dashboard spec v2

### T2.1 Shape

`powerbi-cli.dashboard.v2` is a superset of v1. v1 specs keep working through
an explicit `schema` field check and a documented upgrade path
(`report spec upgrade --spec v1.json --out v2.json`).

```text
schema        "powerbi-cli.dashboard.v2"
report        name, displayName, description, locale, audience, questions[]
model         measures[], measurePatterns[], calculatedColumns[],
              relationships[], staticTables[], dateTable, sortBy[],
              formatStrings[]
style         preset | bundle | tokens {palette, semantic, typography,
              surfaces, spacing, numberFormats}, defaults overrides
layout        grid {columns, gutter, margin}, pageSize, rail {side, slicers[]}
filters       report-scope filters[]
pages[]       id, displayName, size, template, heading, subtitle, filters[],
              slicers[], visuals[], interactions[], drillthrough {target,
              hidden, backButton}, tooltipFor (fixture-gated)
visuals[]     id, type, title, subtitle, bindings[], layout | slot,
              sort, drilldown, topnGuard, filters[], format {…catalog…},
              conditionalFormatting[] (fixture-gated)
proof         desktop {level, pages, expectValues[]}, goldens[]
```

Every section maps to ops from T1. Unknown keys fail per T0.1.

### T2.2 `report spec explain` and `report spec schema`

- `report spec schema --json` emits the JSON Schema for v2 so agents can
  self-validate and so tests can prove the walker and the schema agree.
- `report spec explain --spec x.json --json` prints the compiled op plan
  without writing anything: the exact ordered ops with stage numbers, the
  handles they will create, resolved slot coordinates, the design defaults
  that will apply per visual, and the proof commands that will follow. This
  is the agent's dry run for a whole dashboard.

### T2.3 Missing-input diagnostics

When a section needs data the spec lacks (a TopN guard with no measure, a
drillthrough with no target column, a slot in a template that does not
define it), the compiler returns a structured `spec.missing_input` error
listing the field, why it is needed, and the `report spec fields` query that
would reveal candidates. No guessing.

### T2.4 Composition, versioning, scale

Implemented by `pbi-t2-dashboard-spec-v2-dsd.4`: large schemas and specs can be
composed from bounded relative `$include` fragments. `schemaVersion` is
warning-only for one compatibility release, while `schema normalize` and
`report spec normalize` flatten the supported composition points into
deterministic canonical JSON with sorted `normalizedFrom[]` provenance.
Traversal, canonical-root escape, symlink, cycle, depth, fragment-count, and
fragment-size violations are refused by `IncludeGuard`. Report build consumes
the normalized form, so artifact parity is based on equivalent normalized
documents. The perf test covers a 100-table schema assembled from 50
fragments and enforces the ten-second target; the 512 MiB target remains part
of the CI resource budget.

### T2.5 Spec extraction and spec diff

The loop must close in both directions. `report spec extract --project <pbip>
--out spec.json` produces a v2 spec from an existing project, generated or
Desktop-authored, for the supported subset, and lists everything it could not
express under `unsupported[]` with JSON pointers into the PBIR. `report spec
diff a.json b.json` is a typed diff. Together they give agents the workflow
the roadmap's never-built `clone-template` wanted: open a corporate template,
extract its spec and style tokens, and rebuild for a new schema. Round-trip
property: extract then build then extract is a fixed point for every fixture
in T7.

Tests: schema/walker agreement test; v1 to v2 upgrade golden; one negative
test per `missing_input` case; include cycle and traversal refusal tests;
conformance test that `spec fields` lists every v2 section; extract
fixed-point test per fixture; perf test.

## T5. Design system

This tranche is what turns "valid" into "beautiful". It is opinionated with
escape hatches, never mandatory. Everything it emits goes through the T4
catalog, so nothing here invents PBIR.

### T5.0 Design defaults catalog

A data file, not code branches: `design-defaults.v1` with per-visual-family
defaults expressed as catalog properties and token references. Shipped
values (each overridable under `style.defaults` in the spec):

- Spacing scale 8/16/24/32 px; page margin 24; gutter 16; heading band 56.
- Type scale: heading 20, visual title 14, axis/label 10, card callout 28,
  card label 12; font family from tokens.
- Cards: white surface, 1 px border in `surfaces.border`, no shadow, callout
  in `emphasis` when the KPI has a target, else `foreground`.
- Bar and column charts: data labels on, gridlines off, axis titles off,
  descending sort by the first measure, single accent color unless a Series
  is bound.
- Line and area charts: markers off, subtle gridlines, axis titles off when
  the category is a date, data labels off.
- Scatter: bubble size 20 percent, legend top.
- Tables: header bold in `foreground`, alternating row banding in
  `surfaces.alt`, column widths auto, default sort by the first measure
  descending when one exists.
- Matrix: expand/collapse buttons on when more than one row level, row
  subtotals off by default.
- Slicers: dropdown above twelve distinct values, list otherwise, height per
  the engine minimums, header on with sentence-case title.
- Titles: sentence case, left aligned, `foreground`, no title when the slot
  is a KPI card whose category label already names it.
- Number formats by type: integer with separators, currency two decimals,
  percent one decimal, compact display units above one million.

Every default names the T4 property it maps to; a default whose property is
not yet in the catalog is inert until that property is proven, and `spec
explain` says so.

### T5.1 Layout grid engine

- A page grid model: 12 columns, configurable gutter and margin, row height
  unit; page sizes 1280x720 (default) and 1920x1080 with proportional scaling.
- Page templates as named slot layouts: `kpi-strip-trend-breakdown`,
  `overview`, `time-series`, `ranking`, `distribution`, `comparison`,
  `detail-table`, `drillthrough-detail`, `exception-list`, `matrix-focus`,
  `scatter-focus`, each with an optional `rail-left`/`rail-right` slicer rail
  and a heading band. Each template names slots (`heading`, `kpi.1..4`,
  `primary`, `secondary`, `tertiary`, `detail`, `rail`) with grid spans and
  per-slot preferred visual families.
- `visuals[].slot` resolves to exact coordinates; explicit `layout` wins.
- `report layout auto` gains `--template <name>` and `--grid` overrides and
  becomes the same engine, so post-build relayout is identical to build-time
  layout.
- Minimum-size rules per visual type (slicer 76/104, card, chart, matrix) are
  enforced in the engine, not only in validation.
- Section dividers and heading textboxes are emitted by the template using
  T4.8 shapes and T4.5 typography.

### T5.2 Style tokens and semantic color

- `style.tokens` compiles to a theme JSON (`dataColors`, `background`,
  `foreground`, `tableAccent`, `textClasses` for title/label/callout sizes)
  via the existing registered-resource theme path, plus per-visual object
  defaults through T5.0 and the T4 catalog.
- Semantic tokens: `good`, `bad`, `neutral`, `warning`, `emphasis`, plus one
  sequential and one diverging ramp for conditional formatting. Templates and
  the planner reference semantics, never literal hex.
- Number formats derived from column/measure types and `report.locale`:
  currency, percent, integer with thousands separators, compact display
  units with sensible defaults; written to TMDL `formatString` and to data
  label display units.
- Ship four built-in token sets: neutral corporate, high-contrast, dark, and
  print-friendly. Every text/background pair passes a WCAG AA contrast check
  at build time.
- `report style tokens show/derive`: derive tokens from an existing
  Desktop-authored report so brand material can be captured without copying
  literal text.

### T5.3 Design lint

`report audit --rules design` (also part of `lint`, `triage`, and the
scorecard), each rule with a stable id, JSON pointer, and a sanitize action
where mechanical:

- `design.visual_overlap`, `design.visual_off_grid`,
  `design.visual_outside_page` (exists as `report.visual_outside_page`; keep
  the id stable and add it to the design set).
- `design.row_height_inconsistent`, `design.column_width_inconsistent`
  (siblings on a grid row/column differ).
- `design.page_overcrowded` (visual count above the template budget),
  `design.page_missing_heading`.
- `design.title_case_inconsistent`, `design.title_missing`,
  `design.title_duplicate` (exists; fold in).
- `design.font_below_minimum`, `design.contrast_below_aa`,
  `design.palette_drift` (visual color not in theme palette or semantic set).
- `design.slicer_too_short` (exists as validation; expose as a rule),
  `design.rail_not_synced` (rail slicers differ across pages).
- `design.number_format_missing` (measure without a format string),
  `design.display_units_missing` on large-magnitude labels.
- `design.ranking_not_sorted` (bar chart with a category and no sort).
- `design.drillthrough_no_back_button` once T4.8 buttons are proven.

Every rule ships with a positive and a negative fixture and appears in
`lint --explain <rule>`.

### T5.4 Wireframe preview

`report wireframe export --format svg|html`: a deterministic offline preview
with grid overlay, slot names, visual type labels, titles, and lint markers,
written outside the project. Requested in the 2026-07-14 friction review and
still open. The current wireframe is JSON only; locate and reuse its layout
model. SVG goldens per archetype must be identical across OS in CI.

### T5.5 Auto-improve loop

`report design-plan` exists and already lists opportunities. Upgrade it to
emit an op plan: `report design-plan --project <p> --emit-ops fix.ops.json`
turns every mechanical design lint finding and every accepted opportunity
into typed ops (relayout to a template, apply defaults, add missing sort,
add a heading, add a rail). The agent reviews the plan with `spec explain`
semantics and applies it with T8 `apply`. Lint, propose, apply, re-lint is
the refinement flywheel for an existing report, including Desktop-authored
ones.

Tests: golden SVG per archetype; layout engine unit tests for every template
at both page sizes; lint fixture per rule with a positive and a negative
project; contrast check unit tests; defaults catalog test that every default
maps to a catalog property or is marked inert; auto-improve test that
applying the emitted plan drives design lint to zero on each fixture.

## T6. Planner v2

`report plan` today emits the same seven-visual template for every schema.
Planner v2 must make decisions that visibly depend on the data shape and the
intent, explain each decision, and refuse to guess when signals are weak.

- T6.1 Profile v2: `profile infer --rows <csv|json>` (advertised as planned;
  implement) computing null rates, distinct counts, min/max, top values, time
  coverage, and grain conflicts. Only bounded top values leave the rows, and
  `--redact` replaces literals with counts for sensitive columns.
- T6.2 Shape classification: single flat table, star, snowflake, multi-fact;
  candidate facts/dimensions/date tables; high-cardinality noise; key
  candidates. Emitted in `decisions[]` with evidence. Proposes a date table
  when a date column exists without a date dimension.
- T6.3 Intent parsing: `--intent <file>` with audience, questions, KPIs,
  comparisons, time periods, required drill paths, and alert rules. Questions
  map to archetype choices; each mapping is a decision with a reason.
- T6.4 Rule catalog: visual selection and archetype rules live in a data file
  (`planner-rules.v1`) with explicit conditions and scores (time axis present
  and one measure: time-series; category plus measure: ranking; two measures
  plus category: scatter; many columns and no measure: detail table; measure
  with target: gauge/KPI; alert rules: exception list with conditional
  formatting). `report plan --explain-rules` prints which rules fired and
  their scores. Output is a v2 spec using slots, semantic colors, and a style
  preset, never coordinates or hex.
- T6.5 Cardinality-aware performance guards: when a category's distinct count
  exceeds a threshold, the planner inserts the pilot's TopN guard pattern and
  recommends `Table.Buffer` where a partition reuses intermediates. Every
  guard is a decision with the threshold that triggered it.
- T6.6 Measure library: the planner proposes standard measures from T10.6
  patterns (total, YTD, prior period, period-over-period %, share of total,
  running total, rank) for each KPI and time axis, each validated by
  `dax lint` before it enters the spec.
- T6.7 Weak-signal behavior: when no date column, no measure, or ambiguous
  fact table, return `plan.missing_input` with the exact override field
  instead of a default layout.
- T6.8 `report plan --variants 3`: three distinct spec candidates with
  decision diffs so an agent can pick.
- T6.9 Narrative flow: multi-page plans follow overview, then trend, then
  breakdown, then detail, with the rail replicated and a drillthrough detail
  page when a high-cardinality dimension exists; the flow is itself a rule
  in the catalog.

Tests: planner goldens for at least six materially different schemas (flat,
star, multi-fact, no-date, no-measure, wide-columns); a determinism test; a
test that no two archetype schemas produce identical page structures; a test
that every decision has a non-empty reason and names the rule that fired.

## T8. Batch operations and snapshots

Falls out of T1 almost for free:

## T9. Desktop oracle automation and fixture harvester (parallel Windows track)

Second target. Runs on Windows only, opt-in, never a CI dependency.

- T9.1 `desktop refresh-check <project>`: opens the managed session,
  triggers refresh through the Desktop Bridge where the pinned bridge exposes
  it and through UI automation otherwise, waits for completion, captures
  per-table refresh errors, and returns the failing table/column. Proof level
  `desktop-canvas-refresh` only when refresh completed and no issue dialog
  was observed.
- T9.2 `desktop canvas-check <project> --page <p> --expect <values.json>`:
  after refresh, uses `model dax execute` to assert `proof.expectValues[]`
  and the bridge screenshot to assert a non-blank canvas; records evidence
  outside the project.
- T9.3 Issue banner/dialog detection via the UI automation tree; any modal
  text is returned verbatim in `proof.signals.dialogs[]`.
- T9.4 Process/window cleanup contract unchanged: exact PID ownership, no
  title-wide kills, cleanup result in every response.
- T9.5 Promote fixture proof levels automatically: a passing canvas-check
  writes a `desktop-proof` record that `features list` and
  `desktopProofedArchetypes` read.
- T9.6 Desktop save round-trip: `desktop save-check` reopens the saved copy
  and diffs normalized summaries, so Desktop canonicalization (like the
  `isDefaultSort` removal already recorded) becomes a regression signal.
- T9.7 Fixture harvester: `desktop harvest-reference --project <saved.pbip>
  --visual <handle> --out docs/reference/desktop-authored-visuals/<name>.json`
  copies a Desktop-saved `visual.json` (or page/report fragment) into the
  reference corpus with provenance (Desktop version, date, source project
  fingerprint, license note), strips persisted data values, and refuses files
  that still contain them. Works on Linux for already-saved projects; the
  Desktop-version field is then `unknown` and the entry stays
  `desktop-golden-pending`. This is the command that feeds every T4 bead.

Tests: unit tests for signal parsing and proof-level computation with
recorded fixtures; harvester tests for value stripping and refusal; ignored
Windows-only live tests mirroring the existing exact-toolchain pattern in CI.

## Definition of done for this plan

- `report compose` on an unseen star schema with sample rows and an intent
  file returns a finished project, a scorecard with zero design findings, an
  SVG wireframe per page, and every decision explained.
- `report build` on that spec yields a project that passes strict validation,
  the Microsoft validator on Windows, design lint, handoff check, and
  artifact parity, needing zero follow-up mutation commands.
- The five current archetypes plus twelve new ones are expressed purely in v2
  and render as SVG wireframes offline; extract-build-extract is a fixed
  point for all of them.
- `apply --ops` replays a recorded session byte-identically, and
  `design-plan --emit-ops` drives design lint to zero on every fixture.
- The formatting catalog covers every idiom the pilot hand-patched, and the
  visual catalog includes structure elements (shapes, buttons, images).
- On a Windows machine, `desktop canvas-check` promotes a fixture to
  `desktop-canvas-refresh` without a human click, and `harvest-reference`
  produces the reference files for the next catalog wave.
- README, SKILL.md, `capabilities`, and `features list` cannot drift because
  CI checks them.
- Every measurable target in the table above is met and checked in CI or a
  nightly job.
- Every bead has tests with logging, and `br dep cycles` is empty.
